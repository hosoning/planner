# Arcana v2 — detailed spreads and executable handoff

2026-10-07. Supersedes v1 duration, calibration UI, spread and surprise behavior.

## Calibration
Show the exact precommitted prediction and card before asking `對，符合` / `不對` / `不確定，整輪重抽`. The answer is a boolean acknowledgement, never new factual data for remapping. The server accepts only `yes`/`no`; wrong or skip consumes the entire round and draws all cards afresh. After a failed round, return its audit proof immediately so it is also independently checkable. All conditional formal cards are predrawn without duplication with independent orientations. No later card draws are allowed.

## Granularity
Forty formal positions plus one calibration card. Separate decisions for duration; first meal style; first meal start window; meal count; meal-first; six stop regions; meal character; cuisine; six activity descriptions; six independent yes/no activity confirmations; surprise; gift presence; gift character; pace; transport; rest buffer; rain fallback; photography; shopping; second, third and fourth meal cuisines; final-stop character. A no confirmation rejects the primary activity tag and takes the next ranked feasible category from the original activity card. Conditional decisions are labeled when unused, never silently redrawn.

Duration options: <2h, 4–6h, 6–8h+, overnight. The user's entered availability remains a hard outer window (60 minutes to 24 hours; end may be next day). The selected duration is chosen from the card-ranked feasible durations, with preferred and applied choices both recorded. Meals 1/2/3/4 are similarly constrained by available duration; four means four, never a displayed promise of four with two returned. Meal starts are at least 150 minutes apart. First-meal style: home/reheat, takeaway, ordinary restaurant, premium restaurant. Home is feasible only with a verified supplied home record; no invented home/address. When a preference is unavailable, the output explicitly shows the applied alternative; complete failure returns no itinerary instead of an incomplete one.

Vancouver region choices: Downtown, North Vancouver, Coquitlam, Richmond, Kitsilano, other verified region. Other cities use generic region character and display their real curated area names. Named regions weight curated geography; they do not invent localities. Each final stop shows actual name, full address, area, arrival/departure (with next-day marker), inbound mode/time/cost, waiting/buffer, actual booking page, booking status and source. Bookable restaurants/activities without a verified booking URL are excluded in live mode. Non-reservable walks display `不需預約`; a Google Maps search URL is not a reservation URL. Concrete dishes require an unexpired real menu; symbolic meal descriptions are clearly separate.

## Booking and payments
Booking metadata is operator-curated: required/not required, HTTPS official/operator booking URL, availability checked timestamp, status (not booked by default), deposit type none/included/additional/unknown, amount, deadline, cancellation terms/source. Unknown required deposit or missing required booking URL is ineligible in live mode. Included deposits are not double-counted; additional nonrefundable fees enter the total cost cap. The app performs no purchases or bookings. The user records confirmations. A required booking remains a to-do until marked confirmed; payment to-dos must be resolved before corresponding instructions are presented as ready to execute.

## Surprise and handoff
The locked surprise decision defaults the presentation to a server-redacted view. Do not transmit future stops, formal cards, full audit or gift details in ordinary responses before due time. Browser clock changes must not reveal future stops. Each instruction is released using server time in the destination timezone, early enough for the prior leg plus buffer. Opening the app polls while visible; this is not background push delivery. A user can explicitly exit surprise mode to view the full itinerary, or request an organizer-only handoff file with a spoiler warning. Export Markdown with every venue/address/booking URL, requested slot, number of people, spend cap, deposits/deadlines, cancellation notes, gift brief, and the chronological messages the executor should send. Export a spoiler-free ICS schedule linking back to the private app; the chosen calendar handles alerts. Share/copy/download is a user action; no recipient is invented and no message is sent automatically.

For a real hidden gift, the organizer must supply or confirm the actual gift and total spend. A symbolic gift card is not evidence an item exists or is purchased. UI labels gift as an executor task and reserves a budget allowance; no invented vendor or price. Required deposits show user-facing amount/deadline without unnecessary venue spoilers. If paying personally reveals the merchant, the notice states this. The private site is not made public to enable handoff.

## Durable sessions
Persist passed itinerary and booking tasks in D1 so reloads can resume. Only owner session has access. Keep snapshot commitment separate from the itinerary (revalidation may update operational data, never cards). Stored plans use operator-owned catalog metadata; Google lookup responses and route payloads are not persisted. Persisted itinerary route durations are operator-provided conservative caps, verified against Google estimates at plan time. Data freshness/expiry is visible. Default expiry covers trip completion with bounded retention. Use no-store for API responses, explicit organizer export, and no public token URLs.

## Demo and live
Demo retains clearly fictional addresses and internal example booking pages that cannot accept money; no bogus real restaurant booking links. Real mode remains gated on Google credentials and an enriched operator catalog. No AI/LLM in the app; an external AI can be chosen by the user to execute the exported instructions. Live provider integration still needs credential-backed acceptance testing.

## Tests
Boolean-only calibration, failed-round proof, full fresh draw, 41 unique cards; locked detail decisions; <2h and overnight parsing; meal counts and first-meal timing; exact names/addresses and booking links; deposit accounting; surprise response contains no future name/address/card/URL/audit; server-time reveal order; explicit spoiler export; reload resume; ownership; booking updates; no automatic booking or message transmission.
